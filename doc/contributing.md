## Contributing to HELLFORGE

### Code of Conduct

Be respectful, inclusive, and constructive. This is a hard-forged project —
leave it better than you found it.

### What the project is

HELLFORGE is a Python 3.10+ project (dev/tested on 3.11). The repo is a git
worktree-friendly single repo: `ep_core.py` (kernel), `eshell.py`
(console), `run.py` (CLI), `ep_compiler/` (compiler core), `plugins/`
(drivers), `tests/` (self-contained suites). **`main` is the release
branch**; work happens on feature branches. Never commit directly to main.

### Development setup

```bash
python -m venv .venv
.venv/bin/pip install numpy mido scipy pygame pydub psutil
git clone <your fork> piano-dsl && cd piano-dsl
```

### Running the tests

There is no pytest — every suite is a self-contained `tests/*_test.py` with
its own `test(name, fn)` harness and a summary + exit code at the end.

```bash
.venv/bin/python tests/security_hash_test.py   # X/Y integrity
.venv/bin/python tests/syntax_test.py
.venv/bin/python tests/run_all.py              # the full combined run
.venv/bin/python plugins/krip/tests/test_krip.py
```

**Never commit unless the suite is green.** Every feature needs ≥2 tests
using the existing harness. Any `.py` change requires running the relevant
suites.

### Making changes

- Keep the **smallest change** that satisfies the task; preserve backward
  compatibility. v1–v4 sources still compile (with deprecation warnings);
  new syntax goes into the v5 path.
- **No stubs.** Every advertised feature must work end-to-end
  (source → compile → events → MIDI → render).
- **No phone-home, no private dependencies.** The project is fully
  offline-capable. Any network feature must be gated behind an explicit
  opt-in flag. No personal trust keys, no private servers, no hardcoded
  user paths.
- Match surrounding style: module docstrings, `test(name, fn)` sections,
  section banners.
- Prefer precise line-range edits over whole-file rewrites; deletions need
  explicit confirmation.

### Integrity manifest — important

The repo ships a committed integrity manifest, `SECURITY_HASH.txt`, covering
~56 core files plus a 160-byte triple aggregate (SHA-256 + SHA-512 +
BLAKE2b-512), plus `ep_compiler/_version_key.py` (Technique Y) and the
rotating X store. **After any intentional core change, regenerate and
commit** the manifest and version key together with your change:

```bash
python3 tools/gen_security_hash.py
# commit SECURITY_HASH.txt + ep_compiler/_version_key.py with your change
```

Custom plugin directories added under `plugins/` are covered by
`SECURITY_HASH.local`, regenerated by the updater
(`ep_compiler/update.py`).

### Documentation

Docs live in `doc/` (this wiki) and `docs/agent/` (model-consumable maps);
the authoritative language reference is `SYNTAX.md`. Update user-visible
docs whenever behavior changes. Never fabricate file contents — read the
actual files first. If you change plugin behavior, update the matching
`doc/commands/*.md` and `doc/plugins/*.md` pages.

### Signing

Signing is an **optional, opt-in** feature (`sign --setup`, `sys strict 2`
enables enforcement) — it must never be made mandatory. Commits are not
required to be signed.
